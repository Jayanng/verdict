# Web app

Landing page and app for Verdict, the Ootle jury court. Static site, no build
step, no wallet, no funds.

## Run it

```sh
npm run serve   # serves web/ on http://localhost:8000
```

Open http://localhost:8000/index.html. Pages are hash routed: `#/` home,
`#/app` disputes, `#/dispute/0` dispute detail and proof page, `#/open`
guided four-step dispute form, `#/juror` become a juror, `#/simulate` the
walletless simulation walkthrough.

## What is built

- Home: the one-liner, the trust story, the eight invariants in plain
  language, the honest-limits copy, the "Why only Tari" section with one
  sentence and a proof link per Ootle feature, How it works, and FAQ.
- App: the disputes list, each row opening its proof page.
- Dispute detail and proof page: draw inputs with a recompute button,
  per-item evidence hash checks, panel, commits, reveals, ruling, and the
  escrow's caller rule. Three live tamper checks run in the browser against
  the published inputs: change one draw input and watch the panel change,
  change one byte of evidence and watch the hash check fail, call
  `execute_ruling` as a stranger and watch the caller rule refuse.
- Open a dispute: a guided four-step form (deal, parties, evidence, review)
  that builds a local draft in the browser and hashes each evidence item as
  it is added.
- Become a juror: bond floor 30,000 micro-Tari, fee 5,000 micro-Tari per
  dispute, risks, and the demo pool seeded with known testers and disclosed.
- Simulate a dispute (`#/simulate`): the walletless simulation engine in
  `src/simulation.js`, running the full lifecycle in the browser with no
  wallet, no funds, and no chain. A guided walkthrough opens a dispute,
  draws the panel, commits and reveals, rules, appeals, and settles, with
  deliberate rejections along the way: delay 0, replacement before the
  reveal deadline, settle with one vote, reveal with the wrong salt, appeal
  with the wrong fee. Labelled as a simulation on the page, never as live.

The proof page mirrors the template rules as they stand in
`templates/verdict/src/lib.rs`: panel derivation from draw hash, dispute id,
round, draw domain, and frozen pool; commitment hash of (vote, salt, dispute
id, juror); `execute_ruling(dispute_id, outcome, amounts)` restricted by the
caller-component rule plus the in-method assert plus `OwnerRule::None`. The
shared rules live in `src/verdict.js` and are imported by both the page and
the tests. The mirror covers the settlement matrix, the quorum rule, the
refuse exclusion, the fee deduction before the split, the appeal rules, and
the replacement and fallback rules. Settlement amounts are BigInt end to end
in the simulation, so amounts above the safe integer range keep every
micro-Tari, and `settle` and the no-ruling close take no payout accounts
from the caller: the court derives the payer and payee accounts from the
escrow, as the template does.

Two points where the simulation and the template differ on purpose. The
template freezes the escrow before the pool-size check and relies on the
transaction rolling back; the simulation has no rollback, so it validates,
including the panel-size check, before calling freeze. The template and
the simulation both check the commit and reveal windows now: a commitment
after the commit deadline and a reveal after the reveal deadline are
refused in both rounds.

## Sample data

Everything the app shows is sample data, labelled on every page. The three
sample disputes, the seven sample jurors, and every hash are generated by
`tools/generate-sample-data.mjs` from the template rules, so the proof checks
pass on the sample inputs. Regenerate after any rule change, do not edit
`src/sample-data.js` by hand:

```sh
npm run sample
```

No key is a real person, no hash is on chain, and no amount moved.

## Tests

```sh
npm test             # node --test tests/verdict.test.js, 32 tests
npm run test:parity  # node --test tests/parity.test.js, 74 tests
npm run test:all     # both suites, 106 tests
```

The mirror suite checks the panel derivation, the vote commitment bytes, the
pure JavaScript SHA-256 against node:crypto vectors, majority and split math,
the settlement amounts, the caller rule, and that the sample data is
internally consistent and conserves exactly.

The parity suite proves the simulation in `src/simulation.js` agrees with
the mirror and with the template rules on every rule and every rejection
message: the draw delay minimum, the reschedule rule, the reveal window and
the replacement caller rule, the pool minimums, the draw domain separation,
the quorum rule, the refuse exclusion, the fee deduction before the split,
every cell of the settlement matrix, the appeal path, and the no-ruling
fallback. The engine suite is the other half of the proof, run from the repo
root with the build target set:

```sh
CARGO_TARGET_DIR=~/workspace/verdict-build-target cargo test
```

## Design

NutCheck design language: floating white pill navbar, warm paper `#F6F4EF`,
electric blue `#0018FF`, white cards, near-black ink, letter cards with blue
squares, bold sans headings, checkmark ticker strip. `styles.css` holds the
brand tokens and page layout. `rare-ui.css` holds the component styles only,
kept separate per the isolation rule.

Note on the UI library: Rare UI (https://rareui.com) is a copy-paste React
component registry, not a published stylesheet, so no Rare UI code is vendored
in this static build. The footer carries the attribution link the Rare UI
license asks for. Adopting Rare UI components is a defined follow-up for the
move to React, via the shadcn CLI.

## Not in this part

- The live path via Sapient (reading the live Esmeralda indexer and
  template) is out of scope. The proof page works with published inputs the
  user can paste or that the sample data provides, and labels what is live
  versus sample. The simulation page is labelled as a simulation, never as
  live, and makes no live claim.
- The settlement routing shown on settled disputes is the routing the
  templates settle with: the juror fees come first from the principal,
  capped at the principal, and only the remainder is routed to the payee or
  the payer.
